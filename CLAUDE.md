# CLAUDE.md

Context for working on this codebase. Claude Code reads this automatically when the project is opened, so
anything written here carries across sessions without being re-explained.

## What this app is

**Dugout XI** (formerly "IPL League"; the name was changed because IPL is the cricket board's trademark, so keep
"IPL" out of the product name). The folder, database (`ipl_league`) and Java package (`bettingApp`) still carry the
old names.

A prediction league for friends: pick who wins each IPL match, and the app keeps the score and the money straight.
**No money moves through the app.** People pay each other directly; the app records who has paid, works out who is
owed what, and lets the organizer tick people off as they settle.

Two kinds of game:

- **A league** — everyone pays the whole season up front (`amount_per_contest × total_contests` = `joining_amount`,
  a generated column). Every confirmed member is in every contest automatically. Nothing is paid out until the
  league ends, when the whole season is netted into one `settlement_rows` row per person.
- **A one-off contest** — a single match with its own entry amount. The organizer lets people in one at a time, and
  it settles on its own through `payouts` as soon as the result is in.

## Stack

Spring Boot 3.3.5, Java 21, PostgreSQL 16, Flyway, Lombok, JWT auth. Hibernate `ddl-auto=validate` — **the schema
is owned by Flyway, never by Hibernate**. If an entity and the schema disagree, the app refuses to start; that is
the point.

Frontend: React 19, TypeScript, Vite, React Router. No state library and no data-fetching library — a small
`useLoad` hook does it, deliberately.

Admins are not seeded. Either list emails in `ADMIN_EMAILS` (comma separated; they become admins when they register
and on every startup, see `AdminEmails`/`AdminBootstrap`), or register and run
`update users set role = 'ADMIN' where email = '...'`. After that, admins promote others from Admin → Accounts.
The role is read from the database on every request, so it takes effect at once.

## Features added after the first version

- **Passwords without email** (`auth/PasswordService`): "Forgot password?" alerts the admins in-app (at most once an
  hour per account, same answer whether or not the email exists); an admin issues a temporary password, shown once;
  `must_change_password` makes the app show only the change-password screen until it is replaced. Any password
  change sets `password_changed_at`, and the JWT filter refuses tokens issued before it (whole seconds), which signs
  out every other session.
- **Stats by period** (`dashboard/PeriodStats`, a pure function like PayoutCalculator; `GET /api/me/stats/period`).
  Contests are placed in a period by start time; months are calendar months in India time.
- **Excel exports** (`export/`, Apache POI): a league season for its members (picks only for started contests) and
  a personal history. Column widths are measured by hand because POI autoSizeColumn needs fonts on the server.
- **API reference** (springdoc + Scalar): springdoc generates the OpenAPI description at `/v3/api-docs` from the
  controllers; `common/ApiDocsController` serves a Scalar page at `/docs` (script pinned to an exact version). Both are
  off unless `API_DOCS_ENABLED=true`. **Every new endpoint needs an `@Operation(summary = ...)` and its controller a
  `@Tag` from `ApiDocsConfig.TAGS`**; `ApiDocsTest` fails otherwise. The Postman collection stays as the scripted
  run-through of a season.
- **WhatsApp sharing** is wa.me links built in the frontend (`lib/share.ts`); the app never sends anything itself.

## Decisions already made — do not revisit these without asking

These were settled by discussion. Several look like something simpler would do; each has a reason.

**Money is `BigDecimal` everywhere, and a string over the wire.** Never a `double`, never parsed into a JS number
for arithmetic. A rupee total assembled from floats is how a ledger ends up a paisa out.

**A league's final balance is handed back in full.** Everyone paid the whole season up front, so the organizer
holds the pot, and `final_balance = joining_amount_paid + net_pl` is what the organizer returns to each member.
Nobody ever owes the organizer anything. Only the organizer's own row and a zero balance are settled automatically.
(The code once treated `final_balance - joining_amount_paid` as the transfer, which told losers to pay again and
paid winners only their profit; docs/database-design.md was right all along.)

**The pool formula.** `pool = amount × confirmed players`, `per winner = floor(pool ÷ winners, 2dp)`, and the
remainder is `leftover_amount` on the contest. The leftover is recorded rather than given to somebody arbitrarily,
and the settlement add-up check accounts for it. That is what makes the books balance exactly.

**Everyone is refunded, with nothing spent, in three cases**: no result, nobody picked the winner, everybody did.
In each there is nothing meaningful to split. A player who never picked is a plain non-winner — their entry is in
the pool and they cannot win.

**`PayoutCalculator` is a pure function.** No database, no clock, no Spring. The money rules are the part most
worth testing exhaustively, and they are. Keep it that way.

**Declaring a result takes two steps.** Preview returns a token derived from the result and from every pick that
fed the sums; confirm sends it back and the backend recomputes it. A pick that changed in between means the token
no longer matches and the confirmation is refused. Do not add a one-shot declare endpoint.

**Roles are only `USER` and `ADMIN`.** Whoever creates a league or contest is its organizer, checked per entity —
there is no ORGANIZER role. An admin may act in an organizer's place but is refused without a written reason,
enforced in `AuditService` and again by a check constraint.

**The organizer plays in their own league** and is added as a CONFIRMED, PAID member at creation. In a one-off
contest their own payout is marked PAID_OUT immediately: they hold the pot, so there is nothing to send themselves.

**Nobody joins late.** Requests still waiting when the first contest starts are withdrawn. Letting somebody in
halfway would mean deciding what they owe for matches already played, and there is no fair answer.

**`CANCELLED` is the member-withdrew status**, distinct from `REJECTED` (organizer said no) and `REMOVED`
(organizer took them out).

**Status column names are per table**: `league_member_status`, `contest_status`, `participant_status`,
`payout_status`, `settlement_status`, `payment_status`. Leagues use a plain `status`. This was deliberate — do not
"tidy" them into one name.

**A contest participant keeps the prediction and the result in one row.** A correction overwrites and is audited.

**Teams are stored once** and linked to each tournament through `tournament_teams`. A team plays in many
tournaments, so there is no tournament column on `teams`.

**Money that has moved cannot be quietly changed.** A result correction is refused once a one-off payout has been
marked paid to someone other than the organizer, or once a league member other than the organizer has settled. The
organizer's own balance is always recalculated, because it is the mirror of everyone else's.

**No ShedLock.** The jobs use `FOR UPDATE SKIP LOCKED`, which is enough for several instances of this app.

**Notifications are in-app only.** No email, no push. The frontend polls the unread count.

## Rules the database enforces, not just the service layer

The service checks everything, and then the database checks what would be expensive to get wrong. When changing
either, change both:

- A trigger on `contest_participants` refuses a pick that is late, for a team not in the match, or from somebody
  who is not CONFIRMED. The service checks the clock first; the trigger is the second lock.
- Composite foreign keys: a contest's teams must belong to its tournament, and a league's contest must use the
  league's tournament.
- Check constraints tie money to result: a `WON` row must have winnings above zero, a `REFUNDED` row must have
  spent nothing.
- `audit_log` is append-only — a trigger raises on any update or delete.
- `v_visible_predictions` returns nothing until a contest has started, so a mistake in the service could not leak
  a pick early.

## Conventions worth following

- **A `Clock` bean**, injected everywhere. Nothing calls `Instant.now()` directly, so time is testable.
- **`@Version` optimistic locking** on the mutable entities, plus `findByIdForUpdate` pessimistic locks where two
  requests could race on the same league or contest.
- **`ParticipationService` is `Propagation.MANDATORY`** and so is `AuditService.record`. They must run inside a
  caller's transaction, never start their own.
- **Each participation action checks its own starting status.** The move table alone is not enough — that was a
  real bug once: confirm-payment could skip acceptance because the table allowed `PENDING_APPROVAL → CONFIRMED`.
- **Self-invocation and `@Transactional`.** `ContestStartJob.run()` goes through an `ObjectProvider<ContestStartJob>`
  to call `startOne`, because a call on `this` skips the proxy and the `REQUIRES_NEW` would silently do nothing.
  Watch for this anywhere a job calls its own transactional method.
- **Jobs are off in tests** via `@SpringBootTest(properties = "app.jobs.enabled=false")` on
  `AbstractIntegrationTest`, so a background run cannot change a fixture mid-test. Jobs are tested by calling them
  directly. Do not add an `application-test.yml` that shadows `application.yml`.
- **The frontend's API client is the only thing that calls `fetch`.** Component tests stub `fetch`, not the
  endpoint functions, so the real client runs.
- **`frontend/src/api/types.ts` mirrors the Java response records field for field.** Change a record, change the
  type. The frontend's component tests stub fetch with hand-written fixtures, so they cannot catch a drifted field
  name on their own; that is how the contest winner once went missing from every screen.
- **Never call an `@Transactional` method on `this` from a controller either.** DevToolsController's start-now
  once failed every time for that reason; it now uses a TransactionTemplate.
- **The JVM runs in UTC** (a static block in `BettingAppApplication`, and `-Duser.timezone=UTC` for tests). The
  PostgreSQL driver sends the JVM's zone on connect, and PostgreSQL 16 refuses old aliases such as Asia/Calcutta.
- **The backend decides, the frontend explains.** Every rule is enforced server-side. The screens hide buttons that
  would be refused and ask for a reason up front, but nothing in the frontend is the actual protection.

## Tests

328 backend (as Maven counts them), 62 frontend; `docs/TEST_CASES.md` lists every one. Integration tests start a real PostgreSQL 16 through Testcontainers and run every
migration, so triggers, generated columns and views are exercised rather than mocked. **Docker must be running.**

`src/test/java/.../EndToEndJourneyTest.java` is the one to read first: a whole season through the real API, ending
with assertions that every rupee that went in comes back out.

Helpers: `TestAuth` (registers users, returns bearer tokens), `TestLeagues`, `TestContests` (builds contests, and
nudges times in the database when a test needs a deadline to have passed).

## Known gaps, deliberately left

No sign-in rate limiting. No scorecard feed —
the organizer types the result in, which is why it takes two steps and can be corrected.
